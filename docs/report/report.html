4. Abstract

This report describes the development of ShopKart OIMS, a web application that manages the product catalogue, stock, shopping carts, orders and returns of an online store. It is built with Spring Boot 3.3, Spring Data JPA (Hibernate 6) on a MySQL 8 database, JSP pages with JSTL for the views, and CSS with jQuery for the client side. The code follows the MVC pattern with separate controller, service, repository and entity layers.

Ten tables are mapped to nine entity classes (the wishlist join table belongs to the many-to-many) with ten relationships, including a many-to-many wishlist between customers and products. The repositories contain about twenty custom queries (search with paging, monthly sales, best sellers, low stock, row locking). Seven business rules are enforced in the service layer, and order placement, order cancellation and return approval run as transactions, so stock is never left half-updated. The interface has 21 pages sharing one header, footer and menu, six forms with client-side validation, and six AJAX features such as add-to-cart and live stock check. Three report pages and a dashboard summarise sales and stock. The work is covered by 30 automated tests (unit, query and endpoint tests) and a table of 14 manual test cases, all of which pass.

5. Summary of the Database Design and Changes Made

The Assignment 1 design was not submitted, so the database for this project was designed at the start of Assignment 2, following the scope given for project 4 in Part A. The database models the store around four master tables (category, seller, customer, product) and the transaction tables that are created as customers shop (cart_item, orders, order_item, return_request). A wishlist table links customers and products many-to-many, and a stock_movement table keeps a history of every stock change.

7Indexes on orders(customer_id, order_date), orders(status), product(name)Speed up order history, the status filter and product search.

6. System Architecture (MVC)

The application is a layered Spring Boot application. Each layer only talks to the layer below it. Controllers never use repositories directly for writes; all rules and transactions are in the service layer.

Flow of one request: placing an order

  1. The browser posts the checkout form to POST /checkout (client-side validation has already checked the payment mode).
  2. ShopController.placeOrder() reads the customer id from the session and calls OrderService.placeOrder().
  3. The service method runs inside one @Transactional transaction: it loads the cart, locks each product row (findByIdForUpdate), checks stock, reduces it, writes stock_movement rows, saves the order with its items and empties the cart.
  4. The repositories turn these calls into SQL through Hibernate; MySQL commits everything at the end, or rolls everything back if a BusinessException was thrown.
  5. The controller adds a flash message and redirects to /orders/{id} (Post/Redirect/Get); the JSP orders/view.jsp renders the result.

  • ddl-auto=validate: Hibernate does not create or change tables. On start-up it checks every entity against the MySQL tables and refuses to start if a column or type does not match, which keeps the code and the schema from drifting apart.
  • serverTimezone=Asia/Kolkata: the JVM default time zone is set to the same zone in OimsApplication, so times saved by Java and by MySQL defaults agree.
  • Connection pool: HikariCP (Spring Boot default) with its default settings.
  • The tests use a separate src/test/resources/application.properties pointing to an H2 in-memory database in MySQL mode, so running the tests never touches the real data.

Business rules (enforced in the service layer)

Transactional operations

OperationSteps inside one @Transactional method
T1 Place order
OrderService.placeOrder		Load cart → for each line lock the product row and check stock → reduce stock → add OrderItem with price snapshot → write SALE stock_movement → save order with total → clear the cart. If any line is short a BusinessException is thrown and everything is rolled back (proved by the endpoint test checkout_rollsBackWholeOrderWhenOneItemIsShort).
T2 Cancel order
OrderService.cancelOrder		Check status is PLACED → add each line's quantity back to stock → write CANCEL movements → set status CANCELLED.
T3 Approve return
ReturnService.approve		Check the request is still REQUESTED → calculate refund = quantity × unit price → add stock back → write RETURN movement → set status APPROVED and processed date.

    orderRepo.save(order);
    cartRepo.clearCart(customerId);

}

17. Server-Side Validation and Error Handling

Client-side checks can be bypassed, so all data is validated again on the server:

  • Bean Validation on entities, e.g. @NotBlank, @Email, @Pattern(regexp="[6-9]\\d{9}") for phone, @Pattern(regexp="\\d{6}") for pincode, @DecimalMin("1.00") for price, @Pattern for the SKU. Controllers use @Valid with BindingResult; on errors the same form is shown again with messages next to each field (<form:errors>).
  • Uniqueness checks (email, SKU, category name) are done in the services and reported as field errors with bindingResult.rejectValue.
  • Business rule violations throw BusinessException; controllers catch it and show the message as a red flash message on the page.
  • GlobalExceptionHandler (@ControllerAdvice) turns remaining errors into the friendly error.jsp page with the right status: NotFoundException → 404 “Record not found”; unknown URL → 404; wrong parameter type (e.g. /orders/abc) → 400; uncaught business rule → 422; anything else → 500 (logged, no stack trace shown to the user).
  • ApiController has its own handlers so AJAX calls always get JSON ({"ok":false,"message":...}) with status 400 or 404 instead of an HTML page.

18. End-to-End Workflows

Workflow 1 – Cart to order with stock update (and cancellation)

  1. Select a customer in “Shopping as”, open Shop, click Add to cart (AJAX, BR1/BR2 checked).
  2. Open Cart, change quantities with −/+ (AJAX), continue to Checkout.
  3. Enter/confirm the address and choose a payment mode (client-side validation), click Place order.
  4. Transaction T1 runs. Success: redirect to the order page with “Order ORD-261114-019 placed successfully”. Failure: back to the cart with “Order not placed: Not enough stock for ...” and nothing changed.
  5. Staff open Orders and click Mark shipped / Mark delivered (BR4). While still PLACED the order can be cancelled (T2, BR3) and stock returns.

Verified in the running application: ordering 2 × Wireless Mouse, 1 × Head First Java and 1 × Cotton Kurta reduced stock 45→43, 15→14 and 35→34, wrote three SALE rows in stock_movement and emptied the cart. Trying to cancel the order after it was shipped was refused.

Workflow 2 – Return / refund request

  1. On a delivered order the order page shows a Return button on each line (only within 7 days).
  2. The return form shows how many units can still be returned and a live refund estimate; enter quantity and reason and submit (BR5 checked again on the server).
  3. The request appears in Returns as REQUESTED; staff click Approve (T3: refund = qty × unit price, stock added back, RETURN movement) or Reject.

Verified: return #4 for 1 Wireless Mouse was approved with a refund of ₹599.00, stock went 43→44 and a RETURN movement “RET-4” was logged.

19. Search, Navigation and Pagination

  • The navigation menu in the common header links every module: Dashboard, Shop, Products, Categories, Sellers, Customers, Orders, Returns and a Reports drop-down. The active module is highlighted.
  • Search and filters: products (name/SKU + category), shop (name + category + sort order), customers (name/email + city), orders (order no./customer + status), sellers (name/city), returns (status).
  • Pagination and sorting on four listings – products, customers, orders and shop – with 8 rows per page. Column headers are links (sortlink.tag); clicking again reverses the direction (▲/▼). The pager (pager.tag) keeps the current search, filter and sort in its links.
  • Sort fields are checked against a whitelist in PageUtil, so an unknown field in the URL falls back to the default instead of causing an error.

Problems found during testing and fixed

  • The error page returned HTTP 500 instead of 404 because error.jsp had isErrorPage="true", which makes Jasper force status 500 when an exception attribute is present. The directive was removed. (MockMvc does not render JSPs, so this was only visible in the real server.)
  • Order times were shown 5½ hours behind the stock movement times because the JVM was running in UTC while MySQL used IST. The default time zone is now set to Asia/Kolkata at start-up.
  • The checkbox on the checkout page was stretched to full width by the general input style; a specific CSS rule was added.

24. User Guide

Installation

  1. Get the code: git clone https://github.com/DharmikTrivedi/ecommerce-order-inventory.git
  2. Install JDK 17, Maven 3.9 and MySQL 8.0, and start the MySQL service.
  3. In MySQL Workbench (or the mysql client) run as root: database/create_user.sql.
  4. Load the tables and sample data as the app user:
    mysql -u oims_app -p < database/schema.sql
    mysql -u oims_app -p ecom_oims < database/sample_data.sql
  5. From the project folder run mvn spring-boot:run (or run.ps1 on Windows) and open http://localhost:8080.
  6. To run the tests: mvn test (uses H2, does not touch MySQL).

Using the application

  • Store staff: use the menu to manage Products, Categories, Sellers and Customers (Add / Edit / Delete buttons on each list). Use the search boxes and filters, click column headers to sort.
  • Shopping: choose a customer in Shopping as at the top right. Open Shop, set a quantity and click Add to cart. Open Cart to change quantities, then Proceed to checkout, choose the payment mode and click Place order.
  • Order processing: open Orders, click an order number, then Mark shipped and later Mark delivered. Cancel order is available until the order is shipped.
  • Returns: on a delivered order click Return next to a product (within 7 days), enter quantity and reason. Staff approve or reject it on the Returns page; approval refunds and restocks automatically.
  • Order history: a customer's orders are listed on their details page (Customers → name) and under /my-orders for the selected shopper.
  • Reports: open the Reports menu for monthly sales, top products and low stock; use Print to print a report.

25. Conclusion

ShopKart OIMS meets all the requirements of Part A for project 4 and the minimum numbers of Part G: 9 entity classes on 10 tables with 10 relationships (one many-to-many), 18 custom queries, 7 business rules, 3 transactions, full CRUD for 4 entities, 21 pages with a common layout, 6 validated forms, 6 interactive features, 6 AJAX features, 2 end-to-end workflows, 4 paginated and sortable listings, 3 reports with a dashboard, and 30 automated tests plus 14 manual test cases.

The most useful lessons were about transactions and the gap between tests and the real server. Putting the whole order placement in one @Transactional service method, with a row lock on each product, made the stock logic simple to reason about, and the rollback test proved that a failure leaves no partial order behind. Running the application against MySQL also found problems that the automated tests could not see (an HTTP status forced by a JSP directive and a time-zone mismatch), which showed why manual testing in the real environment is still needed.
